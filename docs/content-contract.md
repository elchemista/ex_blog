# Markdown content contract

The configured Git repository is the canonical source for the blog. ExBlog
reads and writes only `.md` files beneath `EX_BLOG_CONTENT_ROOT`, which defaults
to `content`.

## Repository structure

```text
content/
├── en/
│   └── 2026-08-03-a-complete-example.md
└── it/
    └── 2026-08-03-complete-example-it.md
```

Every language directory must be listed in
`EX_BLOG_SUPPORTED_LANGUAGES`. The canonical filename generated by the agent is
`YYYY-MM-DD-slug.md`. The parser and index also accept a filename without a
date prefix when the front matter contains a valid `date` field.

## Front matter

Each document begins with YAML delimited by `---`, followed by a CommonMark
body:

```markdown
---
title: "A complete example"
slug: "a-complete-example"
lang: "en"
status: "draft"
date: "2026-08-03"
updated: "2026-08-03"
category: "Technology"
tags: ["elixir", "phoenix"]
seo_title: "A complete Elixir example"
seo_description: "A concise description that remains within 160 characters."
cover: "/images/articles/file-sha256.webp"
cover_alt: "An Elixir source-code page"
translation_of: null
---

## First section heading

The article body uses **CommonMark**.
```

Fields:

| Field | Contract |
| --- | --- |
| `title` | editorial title; when omitted during reads, it is derived from the slug |
| `slug` | lowercase letters, numbers, and hyphens; when omitted, it is derived from the filename |
| `lang` | configured language code; when omitted, it is derived from the directory |
| `status` | exactly `draft` or `published`; defaults to `draft` |
| `date` | ISO date in `YYYY-MM-DD` form; it may be derived from the filename |
| `updated` | ISO date of the latest revision; defaults to `date` |
| `category` | optional single category |
| `tags` | YAML list or comma-separated string |
| `seo_title` | optional; agent writes are limited to 60 characters |
| `seo_description` | optional; limited to 160 characters |
| `cover` | HTTPS URL or safe root-relative public path; Telegram uploads use `/images/articles/<sha256>.<ext>` |
| `cover_alt` | accessible alternative text; a Telegram photo uses its caption or a title-based fallback |
| `translation_of` | repository-relative path of the source article |

To connect translations, every variant refers to the same source path. For
example:

```yaml
translation_of: "content/en/2026-08-03-a-complete-example.md"
```

The source article does not need its own `translation_of` field. Its canonical
repository path automatically becomes the group identifier.

## Rendering and validation

`YamlElixir` decodes front matter. `MDEx` renders CommonMark with autolinks,
footnotes, strikethrough, tables, and task lists, then sanitizes the resulting
HTML. JavaScript, HTML event handlers, and unsafe markup are not published.

Malformed YAML, missing front matter, invalid dates, unknown statuses, unsafe
slugs, or unsupported languages produce an `invalid` audit entry. A bad file
does not stop the complete index rebuild and is never exposed on the public
blog.

## Agent writes

Every write follows the same sequence:

```text
validate input
→ resolve a path confined beneath the content root
→ serialize one canonical Markdown file
→ git add and commit
→ fetch, rebase, and push
→ rebuild ETS
→ read the resulting article back
```

An update never changes the slug or language of an existing article. A
translation creates a new draft. Publishing, unpublishing, and deletion mutate
the repository and require confirmation on agent-controlled surfaces.

During article creation, OpenRouter generates the body and optional SEO only after the
Spectre confirmation policy succeeds. SEO output is decoded and normalized into
`seo_title`, `seo_description`, `cover_alt`, and `tags` before the Writer applies
the contract limits and serializes the file.

`ExBlog.Content.Writer` is the only canonical Markdown write boundary. Routing,
Kinetic planning, and prompt rendering may propose an operation, but they never
write repository files directly.

## Telegram cover assets

The authorized administrator may send a photo while `article_creation` is
active. ExGram downloads the bytes through the TDLib file identifier. ExBlog
accepts JPEG, PNG, WebP, and GIF files up to 10 MB, detects the format from magic
bytes, and uses the SHA-256 digest as the filename. The Telegram-provided
filename is never reused.

The public copy served by Phoenix is:

```text
priv/static/images/articles/<sha256>.<extension>
```

The durable backing copy is:

```text
$EX_BLOG_DATA_DIR/assets/images/articles/<sha256>.<extension>
```

At startup, ExBlog validates the backing files and restores them into the
release's static directory. Markdown stores only the public path in `cover`.
Image bytes, Telegram file identifiers, and local TDLib paths never enter front
matter, Spectre state, memory, or chat history.
